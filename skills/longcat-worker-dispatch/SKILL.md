# LongCat 派工契约（主模型 = 工程师 + 监工）

## 0. 生效条件

这份契约是**按需启用**的，不是全局默认：

- 用户在这条对话里点名 LongCat（「子agent走longcat」「用 longcat 做」…）→ 启用。
- 没有点名 → 不要启用，按 DSH 默认方式工作（`subagent` 继承主模型，一切照旧）。
- 启用只影响**这条对话**。不要把它套到用户没要求的其它对话或任务上。

> **硬规则：除非用户在本对话里明确点名 LongCat / longcat_worker，否则一次都不许调用 `longcat_worker`。**
> 不要因为「这活挺烦的」「看起来适合派出去」「用户可能会想要」而自行派工；也不要把 LongCat 当作默认的并发手段。
> 本技能已在清单层面声明 `disable-model-invocation: true`，模型**不能自行加载**本契约——只有你亲手调用它，它才存在。

## 1. 角色分工（不可混淆）

| | 谁做 | 内容 |
|---|---|---|
| **工程师** | 你（主模型） | 读懂需求、勘察现场、定方案、拆步骤、写派工单、验收成果、对用户交代 |
| **监工** | 你（主模型） | 派工、并发调度、催办、判废、返工、必要时自己接手 |
| **手** | `longcat_worker` | 只做单件机械劳动：读一批文件、抽字段、跑命令、改写、列表、统计、起草片段 |

LongCat-2.5-Preview 参数大但**判断力弱**：它能可靠执行明确指令，不能替你做决定。所以：

> **凡是需要判断的，你做；凡是需要体力的，它做。派工单写得越像操作手册，它干得越好。**

## 2. 三条铁律

1. **自己读、自己判断。** 派工前你要已经知道目标、路径、成功标准。不要用派工来「顺便搞清楚」需求。
2. **派工单必须自包含。** worker 是全新子代理，**看不到这条对话的任何内容**。它只知道你在 prompt 里写的东西。
3. **worker 的报告是「主张」，不是「事实」。** 每一份结论都要你亲自验收（复现命令 / 读产物 / 独立核对），否则不得写进给用户的答复。

## 3. 工具怎么用

- 工具名：`longcat_worker`。它跑在 `longcat` provider 的 **LongCat-2.5-Preview** 上，一次调用 = 一个全新的一次性子代理。
- 默认是**前台**调用：等你拿到它的最终文本才返回。适合单件、下一步就要用它结果的任务。
- 要并发：在同一条消息里**多次调用** `longcat_worker`，每次带 `run_in_background: true`，然后继续干自己的活，用 `job_output` 收结果。
- 配额：整池**只有一把 key**（`LONGCAT_KEY_1`），并发共享同一份限额。**同时最多 3 个重活 worker**；轻活可以多一点，但别一口气开 10 个。
- 角色不靠工具区分：只有一个工具，靠**派工单**把它变成研究员 / 改写工 / 核对员。

## 4. 派工单模板（照着填，别省字段）

```
【任务】<一句话说明唯一交付物>
【背景】<必要的上下文事实，2-4 行；不要写你的思考过程>
【文件】只允许读写这些绝对路径：
  - D:\...
【步骤】
  1. <具体动作，含确切命令>
  2. ...
【禁止】
  - 不许改动上面清单以外的任何文件
  - 不许重构、不许顺手修 bug、不许扩展任务范围
  - 不许自己再派 agent
【验收标准】<可判定：文件存在 / 命令输出包含 X / 行数 N / 字段齐全>
【报告格式】
  STATUS: done | blocked | partial
  WHAT I DID: <=5 行
  EVIDENCE: 确切路径 + 确切命令 + 真实输出片段（没验证的标 UNVERIFIED）
  OPEN: 未完成 / 不确定 / 超出任务范围的部分
```

要点：

- **路径一律绝对路径**，必要时把项目根写出来。它会按字面理解。
- **命令写全**（含参数、工作目录），不要写「适当处理」「按需」「等等」。
- **一个 worker 只给一件事**。想让它干三件事就开三个 worker，或在一条消息里并发三次。
- **给格式，不只给目标**。它很会照抄格式，不太会推断你想要的格式。

## 5. LongCat 的脾气（实测）

- 它是**推理模型**：回复里带 reasoning，且 reasoning **计入输出 token 上限**。所以派工单不要指望它「省着说」；工具行已把上限设到 65536。
- **工具调用正常**，支持并行工具调用。所以你可以把「先读 A、再读 B、然后用 pwsh 跑 C」排成明确步骤，它能照做。
- **极其字面**：比喻、省略、"as appropriate"、隐含约定都会掉在地上。字面指令它执行得很好。
- **弱在判断**：面对歧义它倾向于编一个看起来合理的答案，而不是报告"我不知道"。所以验收标准必须可判定，并且要求 `UNVERIFIED` 显式标注。
- 上下文窗口很大（1M），但**不要用长上下文替代清晰指令**：长而含糊的派工单会让它跑偏。短、具体、带格式最好。

## 6. 验收清单（每份报告都要过）

1. 产物真的存在吗？（读文件 / 列目录 / 重跑命令，看真输出）
2. 命令是真跑过还是它复述的？（要它给原始输出片段；必要时你自己重跑一遍）
3. 有没有越界改动？（看它动过的文件清单，确认只在授权范围内）
4. 交付物符合派工单的验收标准吗？
5. 任何一条过不了 → 判废，按第 7 节处置，不要"差不多就行"。

交叉核对值得的时候，**派第二个 worker 去复现**第一个的结论（独立复算 / 反向搜索）。两个 worker 都错的可能性远小于一个。

## 7. 失败处置（有预算，不许死循环）

- 第 1 次失败 → 把错误原文和你的修正**写进新派工单**，重派一次（它不会记得上一次）。
- 第 2 次仍失败 → 简化任务：拆得更小、给更死的命令、或换更笨但更确定的办法（比如让它只做纯文本转换）。
- 第 3 次仍失败 → **自己接手**。同一个坑派三次是浪费你的时间和配额，不是坚持。
- worker 报 `blocked` → 先看它给的阻塞点是不是你把派工单写模糊了；是就补全重派，不是就自己解决。
- **永远不要**把"worker 说不行"当成最终结论交给用户；你要给出你验证过的事实。

## 8. 明确不要做的事

- 不要用 `subagent_fork` 来做 LongCat 的活：它复制你的上下文、**跑在你自己的模型上**，一分钱省不下，还会污染上下文。
- 不要指望 `workflow` 自动走 LongCat：workflow 引擎**没有全局路由覆盖**，只有每个 `agent()` 调用显式传 `{ provider: 'longcat', model: 'LongCat-2.5-Preview' }` 才会走 LongCat，否则继承你的模型。
- 不要指望 `spawn_teammate`（Agent Teams 队友）走 LongCat：队友继承 **Lead 的模型**，配置层改不了。要 LongCat 就用 `longcat_worker`。
- 不要让 worker 决定架构、方案、取舍——那是你的工作。
- 不要把 worker 的原文当成你的最终答复；验收后由你重写、浓缩、给出证据。
- 不要问用户"要不要派工""派给谁""帮我转发一下"——派工是你的职责，用户只给目标。
- 不要派你**无法验收**的活。

## 9. 什么时候别派工

- 单次快速读取、一个判断、一行回答、和用户对话 → 自己做。
- 你自己在上下文里就能完成的事，派出去再收回来只会更慢更贵。
- 派工的价值在于**并发 + 体力**，不在于"看起来像在管理"。

## 10. 收尾

给用户的答复里只出现：结论、证据（路径 / 命令 / 真实输出）、仍未解决的部分。不要叙述你的派工过程，除非用户问了。
